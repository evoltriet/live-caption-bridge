# Build vs. buy

**Reviewed: 2026-08-08. Recheck vendor capabilities and terms before each paid event.**

| Option | Strengths | Risks / costs | Best use |
|---|---|---|---|
| Wordly | Turnkey captions/translation, Vietnamese usage documented, guest-device and venue-display workflows, vendor support | Recurring service cost, internet/vendor dependency, less control over fixed bilingual layout and data flow | Primary option when operational certainty matters most |
| This project with Azure | Owned UI, fixed simultaneous English/Vietnamese lanes, direct fullscreen plus OBS, no app telemetry, transparent cloud usage | Azure setup/usage, internet dependency, operator responsibility, must prove language switching and wedding latency | Rehearsed events with a technical AV operator |
| Gated local provider | Potential airplane-mode operation and predictable marginal cost | Unproven bilingual quality/latency on modest hardware, model packaging/licenses, combined OBS load | Only after every v0.2 gate passes |

Wordly remains the safer turnkey fallback. Its published materials describe Vietnamese use, multilingual captions/audio, attendee devices, and display workflows, but public list pricing and event-specific behavior should be confirmed directly before booking. See Wordly's [USC case study](https://offers.wordly.ai/hubfs/Assets/USC-case-study.pdf) and [government translation guide](https://offers.wordly.ai/hubfs/Assets/Government-Translation-Guide.pdf).

Building is worthwhile for ownership, an intentionally simple operator workflow, permanent bilingual lanes, privacy controls, offline experimentation, and avoiding per-event application fees. It is not automatically cheaper after hardware, Azure use, engineering, bilingual review, and trained operation are counted.

Decision rule: until this app completes the full acceptance suite and two venue-style rehearsals on the exact event rig, buy the supported solution for the primary path and run this project only as a supervised parallel test.
